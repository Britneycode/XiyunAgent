# XiyunAgent 优化实施方案

## 1. 目标与原则

本方案针对高频、重度用户的日常使用，覆盖本地安全边界、代码工作流、会话迁移、前端交互、数据迁移和规模性能。

实施原则：

- 先处理可能造成越权访问或误提交的数据风险。
- 每个阶段都能独立开发、测试和回滚。
- 优先复用现有 Hono、SQLite、React 和共享类型，不提前引入新的基础设施。
- 先解决高频路径，再处理低频扩展能力。
- 代码修改前保留现有行为的回归测试和验收记录。

## 2. 优先级定义

| 优先级 | 含义 | 处理要求 |
|---|---|---|
| P1 | 安全、数据完整性或不可逆操作风险 | 优先处理，必须有自动化回归测试 |
| P2 | 高频工作流明显受阻 | 在核心版本中完成，必须有端到端或手工验收 |
| P3 | 数据规模增长后的性能和效率问题 | 先测量，再按结果决定是否扩展架构 |

## 3. 实施阶段

### 阶段 1：收紧本地访问和网页导入边界（P1）

#### 具体问题

- [packages/server/src/app.ts](../packages/server/src/app.ts) 使用默认 `cors()`，本地 Server 的所有接口都可能被其他来源的网页发起请求。
- [packages/server/src/docs.ts](../packages/server/src/docs.ts) 的网页导入允许 HTTP 重定向，并直接读取目标响应。
- 当前网页导入没有明确拒绝环回、私网、链路本地地址的规则。

#### 实施内容

1. 将 CORS 来源限制为实际的本地 Web 开发地址和桌面渲染器所需来源。
2. 对初始 URL 和每次重定向后的 URL 做地址解析。
3. 拒绝环回地址、私网地址、链路本地地址和不支持的端口范围。
4. 限制响应体大小，超出上限时中止读取。
5. 在审计事件中记录导入来源、最终 URL、拒绝原因和响应大小；不得记录 API Key。

#### 验收标准

- 非允许来源不能调用 Provider、会话、文件和工具接口。
- `localhost`、`127.0.0.1`、私网地址和重定向到这些地址的 URL 均被拒绝。
- 超大响应在达到上限前后都不会写入数据库。
- 普通 HTTPS 网页仍可正常导入并保留来源 URL。

#### 需要补充的测试

- CORS 来源测试。
- IPv4、IPv6、域名解析到私网地址的测试。
- 重定向到禁用地址的测试。
- 超限响应和超时测试。

### 阶段 2：让 Git 提交范围可见、可控（P1）

#### 具体问题

- [packages/server/src/tools.ts](../packages/server/src/tools.ts) 的 `gitCommit` 会先执行 `git add -A`，可能把用户已有的其他变更一并提交。

#### 实施内容

1. 在提交 API 中增加明确的文件范围参数。
2. 提交前获取工作区状态和差异，返回待提交文件清单。
3. Code 页面在确认条中显示文件、增删行数和是否包含已有暂存内容。
4. 用户未明确选择文件时，不自动执行全量 `git add -A`。
5. 取消确认时不得改变暂存区和工作区。

#### 验收标准

- 只选择一个文件时，提交不会包含其他未选择文件。
- 确认前可以看到实际提交范围和差异摘要。
- 取消提交后 Git 状态保持不变。
- 提交事件审计记录范围、提交消息和结果，不记录文件内容和密钥。

#### 需要补充的测试

- 多文件工作区下的选择性提交测试。
- 已有暂存内容与新选择文件并存时的测试。
- 取消、空提交、提交失败和提交成功测试。

### 阶段 3：修复模式与会话状态错配（P2）

#### 具体问题

- [apps/web/src/App.tsx](../apps/web/src/App.tsx) 切换 Chat、Work、Code 时只更新当前模式，没有为每种模式独立保存活动会话。
- Work 和 Code 页面按会话 ID 渲染，但没有再次确认会话模式。
- 任务面板可能收到当前模式与旧会话 ID 的组合。

#### 实施内容

1. 为 Chat、Work、Code 分别维护最近活动会话 ID。
2. 切换模式时恢复该模式最近会话，没有则显示该模式空状态。
3. 渲染 Work、Code 和任务面板前校验会话模式。
4. 跨模式传递内容必须通过显式任务交接或摘要，不隐式复用会话。
5. 重启后从本地设置或服务端会话元数据恢复最近会话。

#### 验收标准

- 在三种模式间反复切换，不会出现模式页面显示错误会话。
- 每种模式都能恢复自己的最近会话。
- 任务只属于匹配的会话和模式。
- 删除或失效会话后，页面回到可操作的空状态。

### 阶段 4：补齐高频交互和视觉一致性（P2）

#### 具体问题

- 设计规格中的归档、附件、快捷键、来源回链和部分 Code 手工验收尚未完整落地。
- 设置页仍有“阶段 6 完善”等过期占位文案，例如 [apps/web/src/SettingsPage.tsx](../apps/web/src/SettingsPage.tsx) 的通用设置区。
- Chat、Work、Code 的错误、加载和确认反馈需要统一。

#### 实施内容

1. 增加会话重命名、归档和恢复入口。
2. 支持键盘发送、停止生成和重新生成，并显示明确状态。
3. Work 回答中的来源链接到文档或资料片段。
4. Code 的终端、Diff、提交确认显示目标、影响范围和结果。
5. 统一三种模式的加载、空状态、错误、离线、权限拒绝和成功反馈。
6. 清理已完成阶段的占位文案，避免页面状态与项目状态不一致。
7. 在窄窗口下验证侧栏、任务栏和抽屉的折叠逻辑。

#### 验收标准

- 主要操作可以只用键盘完成，也可以只用鼠标完成。
- 错误提示说明发生了什么、是否已经修改数据、下一步如何处理。
- Work 结论可以定位到来源文档。
- 高风险 Code 操作在执行前显示目标和影响范围。
- 桌面默认窗口和窄窗口均无内容遮挡或不可达按钮。

### 阶段 5：建立可迁移的数据导入导出（P2）

#### 具体问题

- 当前已有数据库备份和回滚机制，但缺少面向用户的选择性导出、导入和跨安装恢复流程。
- 从 ChatGPT、Claude、Obsidian 等工具迁入时，缺少会话、资料和记忆的映射规则。

#### 实施内容

1. 定义带版本号的导入导出格式。
2. 第一版支持会话、Markdown/TXT 资料、记忆事实和必要来源信息。
3. 导入前提供摘要预览：新增、重复、冲突和将被跳过的内容。
4. 为重复内容定义保留、跳过和覆盖策略，默认不覆盖已有数据。
5. 提供应用内导出、导入、备份和恢复入口。
6. 导出包排除 API Key、运行时密钥和敏感审计正文；导入包写入前验证结构和版本。

#### 验收标准

- 新安装可以从导出包恢复会话、资料和记忆。
- 重复导入不会产生不可控重复数据。
- 不兼容或损坏的导入包在写库前被拒绝。
- API Key 不出现在导出包、预览和日志中。
- 导入失败不会破坏已有数据库。

### 阶段 6：控制数据规模和后台刷新成本（P3）

#### 具体问题

- [packages/server/src/docs.ts](../packages/server/src/docs.ts) 的文档列表返回完整正文且没有分页。
- 文档搜索主要依赖 `%LIKE%`，无命中时还会生成多个三字符滑窗条件。
- 会话列表一次返回全部记录。
- [apps/web/src/TasksPanel.tsx](../apps/web/src/TasksPanel.tsx) 每 3 秒轮询任务，App 还定期刷新候选记忆。

#### 实施内容

1. 会话、文档、事实和任务列表增加分页或游标参数。
2. 列表接口只返回元数据，正文按需加载。
3. 使用代表性资料集测量 LIKE、滑窗检索和 SQLite FTS 的延迟与响应体大小。
4. 只有测量证明需要时，才把文档检索迁移到 FTS。
5. 面板不可见或没有运行中任务时降低或停止轮询。
6. 为任务增加最近活动时间和阶段信息，帮助用户区分等待、运行和卡住。

#### 验收标准

- 大型会话和文档集合下首屏只加载当前页。
- 文档列表响应不包含正文内容。
- 搜索延迟、响应体大小和数据库文件增长有基线记录。
- 任务面板关闭后不继续高频请求。
- 只有性能测试证明必要时才引入新的检索依赖或服务。

## 4. 推荐排期

| 顺序 | 阶段 | 结果 |
|---|---|---|
| 1 | 阶段 1 | 本地 API 和网页导入边界可验证 |
| 2 | 阶段 2 | Git 提交范围可见且不会误带文件 |
| 3 | 阶段 3 | 模式与会话状态稳定 |
| 4 | 阶段 4 | 高频交互和三种模式的反馈一致 |
| 5 | 阶段 5 | 用户可以迁移和恢复主要数据 |
| 6 | 阶段 6 | 在真实规模下控制查询和轮询成本 |

## 5. 通用验收要求

每个阶段完成后运行：

```powershell
pnpm typecheck
pnpm test
pnpm build
```

涉及 Server、文件、URL 或权限边界时，追加 RUNBOOK 中对应的 API 验收；涉及桌面窗口或响应式布局时，追加 Windows 打包启动和手工 UI 验收。

P1 阶段必须有自动化回归测试。P2 阶段必须有端到端或可复现的手工验收记录。P3 阶段必须先记录基线数据，再决定是否扩大实现范围。

## 6. 未决事项

- Pi Runtime 的最终接入方式仍需确定。
- PDF/Office 解析需要评估依赖、供应链策略和安装包体积。
- 可执行 Skill/插件沙箱尚未实现；当前权限声明主要用于校验和展示。
- Code UI、Work 来源回链和 Skill ZIP 导入仍需真实 Provider 与桌面环境复测。
